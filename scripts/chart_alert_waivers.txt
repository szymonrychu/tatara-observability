# Keyed waivers for scripts/check_chart_alert_parity.py.
#
# Format, one per line, and the reason is MANDATORY (a reasonless line is a parse error,
# not a pass):
#
#   <ChartAlertName> <metric> # <why no rule in alerts/ reads this metric>
#
# A waiver says "this chart alert's CONDITION is watched here, by a rule keyed on a
# different metric". It never says "this condition does not matter". If a condition is
# genuinely not worth alerting on, the right change is to delete the alert from the
# producer's chart, not to waive it here - the chart file is the specification of what is
# worth watching, and a waiver that means "we decided not to" makes that specification
# lie.
#
# The key is (alert, metric), not metric alone: two chart alerts can read the same metric
# with only one of them legitimately superseded.
#
# --- 2026-08-23, tatara-helmfile#440: the chart plane was disabled and its 32 alerts
# --- reconciled against this repo. 9 read a metric no rule here read; 6 were ported and
# --- these 3 were already covered by a rule keyed differently.

TataraTasksInflightPinned operator_tasks_inflight # Deliberately replaced, not dropped. The chart rule pages when operator_tasks_inflight sits at the concurrency cap for 2h, but under contract A.6 concurrency gates PODS, not Tasks, so a pinned Task count is not the deadlock signature it was written for. alerts/tatara-operator.yaml:448-453 and :900-906 carry the rules that replaced it on the pod-side saturation signals, and record that reasoning.

TataraTaskRejections operator_task_terminal_total # Re-implemented on operator_task_parked_total. tatara-operator v2.0.0 removed `failed` as a state - a failure now PARKS - so the terminal-state counter is no longer where an exhaustion shows up. alerts/tatara-cd.yaml:31 and :136 watch the park counter instead, which is the surface the current state machine actually reaches.

TataraSweepStalled operator_sweep_last_success_timestamp_seconds # Superseded by "Operator sweep heartbeat stale" (alerts/tatara-operator.yaml), which is the same per-(project,activity) sweep deadman keyed on operator_sweep_next_expected_timestamp_seconds instead. PORTING THIS ONE WOULD BE A REGRESSION, not a gap being closed: the chart rule is a FLAT staleness threshold (sweepStaleAfterSeconds, 10800s), and this repo deliberately removed exactly that shape - the comment at alerts/tatara-operator.yaml:1433-1445 records that a flat 21600s threshold was breached for roughly 18 hours of every 24 by the nightly 0 3 / 0 6 crons. The replacement reads a next-expected timestamp the operator computes per (project, activity) from that activity's own cron, so cadence lives in the producer, one rule covers every activity of every Project, and it additionally fires on NoData - strictly more coverage than the chart rule, not less.
